# Архитектура

## Компоненты
- **`local-server/`** — работает дома (Raspberry Pi / мини-ПК), рядом с Mosquitto (MQTT). Слушает Tasmota-устройства, отдаёт REST/WS API, отдаёт саму веб-страницу. Может работать вообще без интернета.
- **`cloud-relay/`** — деплоится в Dokploy как обычно (git → Dokploy). Не хранит логику устройств — только проксирует команды/статус между внешним клиентом и домом. `local-server` сам открывает исходящее WS-соединение к релею (не нужно пробрасывать порты из дома наружу).
- **`web/`** — один и тот же статический PWA-клиент, раздаётся и `local-server`, и `cloud-relay`. При загрузке пробует достучаться до локального сервера по LAN-адресу (короткий таймаут) — если получилось, работает напрямую и офлайн-safe; иначе идёт через облачный релей.

## Протокол Tasmota (MQTT)
- `cmnd/<topic>/POWER` ← команда `ON` / `OFF` / `TOGGLE`
- `stat/<topic>/POWER` → текущее состояние
- `tele/<topic>/STATE` → периодический JSON-статус (тоже содержит `POWER`)

`<topic>` — это значение `%topic%`, которое задаётся в веб-интерфейсе Tasmota при настройке устройства (Configuration → MQTT). Соответствие "topic ↔ человеческое имя" задаётся в `local-server/devices.json`.

## Аутентификация
- `LOCAL_TOKEN` — токен для доступа к API `local-server` из локальной сети. Общий для всех
  устройств в доме. Придумывать и вписывать его в `.env` не нужно: если переменная не задана,
  `local-server` сам генерирует случайный токен при первом запуске, сохраняет его на volume
  (`local-server/docker-compose.yml` / `-v ...:/app/data` в `deploy-to-nas.sh`) и печатает в
  лог (`docker logs domovoy-local-server`). Оттуда его один раз вписывают в настройки (⚙)
  первого клиента; остальные устройства подключаются через QR-пейринг (⇄), без повторного
  ввода. Раздельной аутентификации пользователей в локальной сети пока нет — токен общий.
- IP-адрес `local-server` в домашней сети известен заранее и зашит как дефолт в
  `web/src/config.js` (`DEFAULT_LOCAL_URL`) — вводить его в настройках тоже не нужно,
  разве что оборудование сменится.
- `RELAY_TOKEN` — общий секрет между `local-server` и `cloud-relay` (для установления туннеля дом → облако).
  Он же защищает `GET /api/installations` — список зарегистрированных облачных инсталляций.
- Облачный токен веб-клиента — **не задаётся вручную**. Каждое устройство при первом обращении
  к `cloud-relay` само вызывает `POST /api/register` (можно передать `alias`), получает свой
  токен и сохраняет его у себя (`localStorage`). `cloud-relay` хранит список таких инсталляций
  (`alias`, `createdAt`, `lastSeen`) в `cloud-relay/src/installations.js`, персистентно —
  на volume `/app/data/installations.json` (см. `cloud-relay/docker-compose.yml`).
  Это сознательно открытая регистрация (кто знает адрес релея — может зарегистрироваться и
  подключиться к домашним устройствам): для личного использования секретности самого адреса
  достаточно, но это не полноценная аутентификация пользователей.
  Посмотреть список инсталляций глазами, а не curl'ом — `GET /admin` (сама страница без
  секретов, токен вводится в браузере и хранится в его localStorage).

## Известные ограничения v0.1 (осознанно упрощено для MVP)
- Регистрация облачных инсталляций открытая (см. выше) — вместо полноценных пользователей/сессий.
- `cloud-relay` держит только одно активное соединение с домом одновременно (это и не нужно иначе).
- Веб-клиент переопределяет режим (локально/облако) раз в 15 секунд простым переподключением — работает, но не самый элегантный способ.
- Нет истории состояний/графиков — только текущее состояние.
- HTTPS/WSS для `cloud-relay` обеспечивается Traefik в Dokploy (сертификат не настраивается в этом коде).
